### 1.1 As-found verdict (pre-resolution)

**NO — blockers remain.** The branch did **not** meet the SRD §11 definition of done *as reviewed*.

The "one log, one reducer, derive everything" backbone is genuinely real and well-tested on real code paths: the durable log is a proven superset (INV-1), the single reducer drives both live and rebuild for the SDK/delta/steering kinds (INV-4), the three-way read-path round-trip reads one real broker through three independent surfaces (INV-5 happy path), seq-resume incl. the capture-window fix is asserted against an independently-seeded idempotent log (INV-8), and the REST delivery contract never reports an unconfirmed message as delivered (FR-5/INV-7). 238+ default-tier tests are green.

However, **§4.4 "no silent loss" and the "what you saw live == what you replay later" promise are not fully met**, and §11 has two hard failures:

- **§11.1 (every FR implemented):** FR-3 (one reducer) and FR-4/INV-3 (conflict detection) are **partial** — the live `result`-close is a hand-written fork that diverges from the shared reducer, and `detect_conflicts` has **zero production callers**.
- **§11.4 (reproduce-then-fix the "message not received" symptom):** there is **no dedicated before/after regression test** pinning the old false-success behavior; only the new contract is asserted.
- INV-3, INV-5, and the crash-loss half of INV-2 are each **partially closed** with at least one demonstrable counterexample on a real path.

Two findings are **blocker**, eight are **major**, six are **minor**. The blockers (INV-3 unwired conflict detection; live-vs-rebuild `result`-fold divergence) directly contradict invariants the SRD makes load-bearing and are both reproducible on real code paths.

## 4. Consolidated Findings (deduped, by severity)

### BLOCKERS

#### B-1 — INV-3 conflict detection is never wired into any production path
- **Severity:** blocker · **Confidence:** high · *(merges durability "blocker" + fr-inv-matrix "major" + the INV-3 gap verdict)*
- **Evidence/repro:** `detect_conflicts` is fully implemented (`src/volundr/adapters/outbound/pg_session_event_log.py:76`, `src/volundr/domain/ports.py:609`) and exhaustively unit-tested (`tests/test_adapters/test_session_event_log_conflict.py`, 17 cases), but **`grep -rn detect_conflicts src/` shows zero production callers** (validation-lead confirmed: only the two definition sites). The ingest endpoint `rest_session_log.py:196` and the broker flush both call `append()` → `INSERT ... ON CONFLICT (session_id,seq) DO NOTHING`. **Repro:** append `seq=5 payloadA`, then `seq=5 payloadB` through the same repo (or POST two distinct payloads to the same `(session_id,seq)` at `/sessions/{id}/log`) — the second is silently discarded, no signal raised. INV-3 explicitly requires "conflicting-but-distinct payloads are **detected, not silently swallowed**." The detector is a tested-but-unwired dead capability; the suite gives false confidence the invariant holds end-to-end.
- **Suggested fix:** Call `detect_conflicts` on a real path — the ingest append handler and/or the broker flush, or a periodic integrity sweep on `read_after` — and emit a loud, queryable `log_conflict` sentinel (mirroring `log_gap`) or surface the conflicting seqs in `LogAppendResponse`. Add a test that drives a conflicting append **through the wired path** (not the isolated detector) and asserts the conflict is surfaced.

#### B-2 — Live `result`-fold injects text the shared reducer drops (INV-4 / FR-3 divergence)
- **Severity:** blocker (re-introduces the exact live-vs-replay drift Epic B set out to kill) · **Confidence:** high · *(one-reducer-capture finding #1+#2, validation-lead re-confirmed against source)*
- **Evidence/repro:** Live (`src/skuld/broker.py:3389-3396`): when `not self._pending_assistant_content`, it sets content from `data.get("result","")` **and then scans `data["content"]` text blocks**. Shared reducer (`src/niuu/domain/transcript_reducer.py:463-466`): `if acc.is_empty(): acc.content = str(p.get("result","") or "")`, where `is_empty()` (`:105-106`) is true only when content AND parts AND reasoning are all empty, and it **never reads `p["content"]`**. So for an assistant turn that produced only a `tool_use` part (no text) closed by `result:{result:"DONE"}`: **LIVE content == "DONE", REBUILT content == ""**. The parity suite misses it because `tests/test_domain/test_transcript_reducer_parity.py:251` uses `result:""` and the rebuild test `tests/test_domain/test_transcript_rebuild.py:144-147` asserts only part-types, **never `content`**, for the tool_use+result case. This is "what you saw live != what you replay later" on the most common real shape (agent does tool work, then result carries the summary text).
- **Suggested fix:** Route the live result-close through the shared reducer's policy — add `apply_result_content(acc, payload)` injecting result/content-block text under the SAME `acc.is_empty()` guard and call it from `broker.py` instead of the `3389-3396` block; OR teach the reducer's `result` branch to read `p["content"]` text blocks too. Then add a parity case (tool_use-only turn + non-empty result text) asserting live == rebuilt `content`, and add a `content` assertion to `test_transcript_rebuild.py:144-147`.

### MAJOR

#### M-1 — Pending→active backstop can mark a NEVER-delivered message "active" (false "consumed") on non-native transports
- **Severity:** major · **Confidence:** medium · *(delivery-integrity)*
- **Evidence/repro:** On non-native transports, `_handle_cli_event` flips EVERY pending user turn to active when any assistant-with-content/result/error frame arrives (`broker.py:3133-3145` → `_activate_pending_user_turns_backstop` `:4145-4158`, unconditional pending→active). A message whose delivery is still mid-retry sits at `pending` (logged at `:3778` before the deliver task ran). If a genuine transport `error`/`result`/`assistant` frame is processed while delivery is still retrying, the backstop flips the undelivered turn to "active"; when the retry then terminally fails, `_mark_user_turn_failed` (`:4030-4044`) sees `state=='active'` and returns False, **leaving it active**. The durable transcript then shows the message as consumed-by-the-agent when the agent never received it — exactly the §3.4 class of bug. No test covers the backstop-vs-terminal-failure interleaving.
- **Suggested fix:** Track msg_ids with a live deliver task (or a "delivering" sub-state) and exclude them from `_activate_pending_user_turns_backstop`; only flip turns the transport could plausibly have consumed. Add an interleaving test asserting the turn ends "failed", never "active".

#### M-2 — Hard-crash loses unflushed buffer with no sentinel and no read-side gap detection (durability floor incomplete)
- **Severity:** major · **Confidence:** high · *(durability + fr-inv-matrix, merged)*
- **Evidence/repro:** SRD §8 promises "persist-before-broadcast + WAL/disk-spill + loud overflow sentinel" and INV-2 requires "overflow/**crash** loss emits a queryable sentinel." Persist-before-broadcast and the overflow sentinel exist, but **no WAL/disk-spill was implemented** (grep for `spill|WAL` in `broker.py`/`config.py` is empty; flush is in-memory every `event_log_flush_interval_ms=500`, `config.py:387`). A SIGKILL/OOM between flushes loses every buffered-but-unflushed frame; on restart `_init_event_log` resumes at head+1, so stored seqs stay contiguous 1..N while the crashed run's tail vanishes untraceably. No reader detects the loss — the only gap signal is an explicit `log_gap` frame (`transcript_reducer.py:367`) a dead broker cannot emit. Only §3.3 loss *mode 1* (overflow) is closed; *mode 2* (crash) is silent.
- **Suggested fix:** Implement the promised async disk-spill/WAL for the unflushed tail with a crash-recovery test, OR add read-side seq-discontinuity detection (flag any hole between consecutive stored seqs as a synthetic gap so crash-loss is queryable). If WAL is genuinely descoped, **down-scope §3.3 mode 2 / INV-2 in the SRD explicitly** — do not leave INV-2 claiming a sentinel a crash never produces. Separately add a flush+`read_after` round-trip test proving the overflow sentinel persists at a stable non-colliding seq.

#### M-3 — Broker crash mid-pending leaves a permanently "pending" user turn with no re-drive or reaper
- **Severity:** major · **Confidence:** high · *(delivery-integrity)*
- **Evidence/repro:** The delivery retry task is in-memory (`asyncio.create_task` at `broker.py:3818`, loop `:3989-4028`). The user turn is durably logged `user_confirmed/pending` FIRST (`:3768-3808`), flipping to active/failed only via frames the still-running broker emits. If the broker dies after accepting (pending logged) but before delivery succeeds or terminally fails, no `user_active`/`user_delivery_failed` is ever logged — the rebuild reconstructs "pending" forever and the agent never received the message. FR-5's "survives transport warm-up" holds only within the broker lifetime; resume has no re-deliver path (`_activate_pending_user_turns_backstop` is the only `pending` consumer). This is within the *letter* of INV-7 (pending != delivered, queryable) but is an unhandled silent-stall: a message the operator believes is in-flight (REST returned 202 pending) is never delivered and never failed.
- **Suggested fix:** On broker resume/init, scan rebuilt turns for user turns still `pending` whose owning deliver task is gone and either re-enqueue delivery (idempotent on msg_id) or flip them to visible `failed` via `_fail_user_delivery`. Add a test that kills/recreates the broker mid-pending and asserts the rebuilt turn ends `delivered` or `failed`, never bare `pending`.

#### M-4 — Overflow sentinel "dropped" count under-reports actual loss under sustained overflow
- **Severity:** major · **Confidence:** high · *(durability; validation-lead re-confirmed `broker.py:4801-4831`)*
- **Evidence/repro:** In `_enqueue_event_log`, each overflow does `dropped = buffer[:overflow]; del buffer[:overflow]; insert(0, sentinel{dropped: overflow})`. When overflow recurs, the prior sentinel sits at index 0 and is re-included in the next `dropped` slice, so the new sentinel preserves `first_seq` (correct, since the old sentinel carried it) but **resets `dropped` to only the latest iteration's count**. 20 enqueues into `event_log_max_buffer=5` yields one sentinel reporting `dropped=2` while ~14 real frames are missing (`first_seq=1,last_seq=15`). Both tests (`test_log_superset.py`, `test_event_log.py:69`) assert only `dropped >= 1`, never `dropped == hole size`, and exercise only gentle single-frame overflow.
- **Suggested fix:** Accumulate the prior sentinel's count (`dropped += old_sentinel.payload['dropped']`) when folding it into a new overflow, OR derive `dropped = last_seq - first_seq + 1`. Add a sustained/bursty overflow test asserting `dropped == last_seq - first_seq + 1`.

#### M-5 — Cold-read/replay surface per-connect system+capabilities frames a live client never saw (INV-5 false for any reconnected session)
- **Severity:** major · **Confidence:** high · *(read-path + durability, merged; validation-lead confirmed `NON_BROADCAST_KINDS = {conversation.turn}` only and `_safe_send_broker_frame_to` enqueues)*
- **Evidence/repro:** On every browser connect the broker appends a `"Connected to session {id}"` system frame (`broker.py:6020`) and a capabilities frame (`:6032`) via `_safe_send_broker_frame_to`, which `_enqueue_event_log`s them with fresh monotonic seqs. A live client sees exactly ONE welcome+capabilities pair (its own). But the durable log accumulates one pair PER historical connect. Cold-read (`rest_session_log.py:251`) excludes only `NON_BROADCAST_KINDS` (`= {'conversation.turn'}`); `system`/`capabilities` are not in it and pass `filter_internal_blocks` verbatim, so all N pairs surface. Replay (`ws_session_replay.py:313`) re-streams them in the tail on top of its own preamble. **Repro:** connect a browser twice, then `GET /api/v1/forge/sessions/{id}/log` — observe two "Connected to session" frames; a single live viewer saw one. The headline equality test drives exactly one connect.
- **Suggested fix:** Treat per-connection handshake frames as non-durable (send via a non-logging `_safe_browser_send_json`) OR add their kinds to `NON_BROADCAST_KINDS` so the raw read paths exclude them — they are addressed to one socket, not the canonical shared stream. Add a multi-connect cold-read == single-live-connect equality test.

#### M-6 — Room-mode suppressed transport echoes are logged-but-not-broadcast, then resurface on cold-read/replay (INV-5 false in room mode)
- **Severity:** major · **Confidence:** high · *(read-path; validation-lead confirmed `_enqueue_event_log(data)` precedes the suppress gate at `broker.py:3040` vs `:3150-3165`)*
- **Evidence/repro:** `broker.py:3040` enqueues EVERY transport frame as the first statement of `_handle_cli_event` — **before** the `suppress_channel_broadcast` gate (`:3150-3165`) drops `user/assistant/content_block_delta/result` from the LIVE broadcast when `_pending_explicit_human_response_count>0`. - **Suggested fix:** Either (a) compute suppression before the enqueue and skip `_enqueue_event_log` for frames that will be suppressed, or (b) record a correlation marker on suppressed echoes and exclude it on the raw read paths the same way `conversation.turn` is excluded. Add a room-mode cold-read == live equality test.

#### M-7 — Live internal-visibility default is hardcoded while read-path defaults are config-driven (INV-10 default parity coincidental; §3.5 divergence not closed)

#### M-8 — WS-proxy unregisters the live port on a transient broker-leg blip with no re-registration (RUNNING-but-unreachable strand)
- **Severity:** major · **Confidence:** medium · *(liveness-routing)*
- **Evidence/repro:** In `src/niuu/app.py:753-763`, when the browser leg accepted but the broker leg `ws_client.connect` raised (`connected==False`), the `finally` block calls `skuld_reg.unregister(session_id)` **before** `skuld_reg.reconcile_dead(session_id)`. ## 5. §3.4 "message not received" root-cause — reproduced-then-fixed?

**Partially.** The §3.4 root cause (inbound messages confirmed before delivered) is **substantially closed in current behavior** but **NOT pinned by the §11.4 before/after regression test** the DoD requires.

- **Fixed-behavior is well proven.** A message is durably logged `user_confirmed/pending` (not "sent") FIRST; bounded retry (`broker.py:3989-4007`); terminal failure → visible `failed` turn (`:4012-4044`); delivery-time route recomputation (`:3892`). The REST bridge (`rest.py:2498-2533`) returns 200 delivered / 202 pending / 502 failed / 409 unreachable and **never reports an unconfirmed message as delivered** — asserted by `tests/test_adapters/test_rest.py::TestSessionMessages::{test_send_message_delivered_ack_returns_200_delivered,test_send_message_failed_ack_does_not_report_success,test_send_message_no_ack_reports_pending_not_sent}`. No path was found where the REST API reports a non-delivered message as delivered/"sent".
- **§11.4 is NOT satisfied.** There is no test that reproduces the *old* false-200 "sent" path then shows it fixed (grep for "message not received"/"false success" finds none) — see **m-2**. The acceptance criterion is documentary, but it is an explicit DoD item and currently unmet.
- **Two residual states still diverge from what the agent received** (neither a false-success, both transcript-correctness regressions): a broker crash mid-pending strands a permanently `pending` turn (**M-3**), and the pending→active backstop can mark a never-delivered message "active" on a racing non-native transport frame (**M-1**) — re-introducing the §3.4 class of "transcript shows a message the agent never got."

**Conclusion:** the live false-success bug is fixed in code and covered by current-behavior tests, but §11.4's reproduce-then-fix is not present, and two racy/crash interleavings re-open the §3.4 failure mode.
