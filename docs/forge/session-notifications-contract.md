# Session notifications: build contract

Status: binding for the `forge/session-notifications` build, 2026-09-23. The
architecture and rationale are in [session-notifications-plan.md](session-notifications-plan.md).
This file fixes the interfaces that separate workstreams build against. Any change
to a section marked **(shared)** needs agreement from every consumer.

Shared Python contract: `src/niuu/domain/notifications.py` **(shared)**. It holds the
kinds, severities, sources, links, `NotificationDraft`, the deterministic ids
(`notification_id`, `turn_dedupe_key`), the turn builder and parser
(`build_notification_turn` / `draft_from_log_payload`) and `summarize_reply`.
Import it; do not re-declare it.

## 1. The notification turn in the session log (shared)

The broker appends a `conversation.turn` produced by `build_notification_turn`,
using the same append path as present-file.

- `turn.id`: `nt_<32 hex>`, generated by the broker.
- `turn.role` is `assistant` and `turn.content` is the title.
- `turn.parts[0]` is a `tool_use` with `name` `forge_notification` and
  `input` = the draft, plus `notification_id`.
- `turn.metadata` is `{kind: "notification", notification: <same input>}`. It
  never sets `final_output`.
- The draft may carry one `image` reference (§11). It appears in `input` only when
  set, so turns without an image keep their earlier shape.
- The question signals `question`, `about_question` and `ask` (§12) follow the same
  rule: present in `input` only when set.
- So does the speak intent `speak` (§13).

Notification id: `notification_id(turn_dedupe_key(session_id, turn.id, kind))`,
where `session_id` is the Forge session UUID string.

## 2. Storage: migration `000084_forge_notifications` (core)

Idempotent SQL in `migrations/`, which the Helm chart and the CLI bundle read directly.

```sql
forge_notifications(
  id UUID PRIMARY KEY,                 -- notification_id(dedupe_key)
  seq BIGSERIAL NOT NULL UNIQUE,       -- feed cursor, commit-ordered per node
  dedupe_key TEXT NOT NULL UNIQUE,
  session_id UUID NULL, session_seq BIGINT NULL, session_name TEXT NULL,
  owner_id TEXT NOT NULL, tenant_id TEXT NULL, project_id TEXT NULL,
  kind VARCHAR(32) NOT NULL, severity VARCHAR(16) NOT NULL, source VARCHAR(16) NOT NULL,
  title TEXT NOT NULL, body TEXT NOT NULL DEFAULT '', links JSONB NOT NULL DEFAULT '[]',
  engine TEXT NULL, model TEXT NULL, correlation_id TEXT NULL,
  metadata JSONB NOT NULL DEFAULT '{}', created_at TIMESTAMPTZ NOT NULL DEFAULT now())
  -- idx (owner_id, seq), (session_id, seq), (project_id, seq), (kind, seq); no FK to sessions
forge_notification_read_states(user_id TEXT PRIMARY KEY, read_through_seq BIGINT NOT NULL DEFAULT 0,
  revision BIGINT NOT NULL DEFAULT 0, updated_at TIMESTAMPTZ NOT NULL DEFAULT now())
forge_notification_rules(id UUID PRIMARY KEY, owner_id TEXT NOT NULL, name TEXT NOT NULL,
  enabled BOOLEAN NOT NULL DEFAULT TRUE, match JSONB NOT NULL DEFAULT '{}',
  sink VARCHAR(64) NOT NULL, integration_connection_id TEXT NULL,
  config JSONB NOT NULL DEFAULT '{}', quiet_hours JSONB NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now())
  -- idx (owner_id)
forge_notification_deliveries(id UUID PRIMARY KEY,
  notification_id UUID NOT NULL REFERENCES forge_notifications(id) ON DELETE CASCADE,
  rule_id UUID NOT NULL REFERENCES forge_notification_rules(id) ON DELETE CASCADE,
  sink VARCHAR(64) NOT NULL, status VARCHAR(16) NOT NULL DEFAULT 'pending',
  attempts INTEGER NOT NULL DEFAULT 0, next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  lease_until TIMESTAMPTZ NULL, last_error TEXT NULL, delivered_at TIMESTAMPTZ NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (notification_id, rule_id))
  -- idx (status, next_attempt_at)
```

Delivery `status` is one of `pending | claimed | delivered | failed | dead | suppressed`.
`suppressed` means the rule matched but quiet hours or the rate limit held the
message back. The row is kept for audit.

Dedupe keys:
- **Agent turn:** `turn_dedupe_key(session_id, turn_id, kind)`.
- **reply_ready:** `turn_dedupe_key(session_id, final_turn_id, "reply_ready")`.
- **attention** (needs input): `attention:{session_id}:{state_since ISO}`.
- **Direct submit:** `submit:{session_id or "-"}:{principal}:{idempotency_key}`.

## 3. Projection (core)

After the log append in `POST /sessions/{id}/log` returns, and **before** the 201
response, Forge projects the batch. It uses the *stored* rows (not the request
payloads) for the batch seqs, excluding conflicted seqs:

- A notification turn (`draft_from_log_payload`) becomes an agent notification.
  - `source` is `agent` and `session_seq` is the row's seq.
- A final output (`is_final_output`) becomes a `reply_ready` notification.
  - `source` is `system`, `severity` is `success`.
  - Title and body come from `summarize_reply(content, …)`, with limits from
    `NotificationsConfig`.
  - It is only created when `notifications.reply_ready.enabled` (default **false** since
    2026-09-28: one per final reply was noise; agents send a `milestone` when a task is done).

The notification insert (`ON CONFLICT (dedupe_key) DO NOTHING RETURNING`), rule
evaluation and the delivery inserts happen in **one transaction**. Rules are
evaluated only for newly inserted rows. After commit, each new row is broadcast as
the SSE `session_notification`. Producer retries are safe: a duplicate yields
no new row, no new delivery and no broadcast.

`update_activity`, when it publishes `SESSION_NEEDS_INPUT`, also records an
`attention` notification (severity `warning`, `source: system`) through the same
service path.

Ownership: `owner_id`, `tenant_id`, `project_id`, `session_name`, `engine` and
`model` come from the session row at projection time.

## 4. REST API on Volundr under `/api/v1/forge` (shared: core, facade, web, skuld)

The notification JSON (`NotificationResponse`):
```json
{"id":"uuid","seq":12,"session_id":"uuid|null","session_seq":34,"session_name":"…",
 "owner_id":"…","tenant_id":"…","project_id":"…|null","kind":"milestone","severity":"info",
 "source":"agent","title":"…","body":"markdown","links":[{"label":"…","url":"…","kind":"url","file_id":null}],
 "engine":"claude|codex|…|null","model":"…|null","correlation_id":null,
 "image":{"url":"/api/v1/forge/notifications/{id}/image",
          "thumbnail_url":"/api/v1/forge/notifications/{id}/image?variant=thumb",
          "mime":"image/png","width":1200,"height":800,"alt":"…|null"}|null,
 "image_state":"pending|ready|failed|null","image_error":"…|null",
 "question":true|false|null,"about_question":{"id":"question:<host>:<uuid>","action":"relay"}|null,
 "ask":{"items":[…]}|null,"input_request":{"kind":"question","request_id":"…|null"}|null,
 "speak":{"text":"…","priority":"now|next_window"}|null,
 "created_at":"ISO-8601","read":false,"instance_id":"<added by the Guild facade>"}
```
`image` is present only when Forge holds a stored copy (§11); `image_state` is null
when no image was attached.
`read` is computed per reader as `seq <= read_through_seq` **or** an individual
acknowledgement in `forge_notification_reads(user_id, notification_id, read_at)`.
Opening a card must not advance the host watermark or clear other unopened cards.

`turn_id` is the transcript turn the notification anchors to: the notification's own turn
(`nt_…`) for agent notifications and the final reply turn for `reply_ready`. It is `null`
when there is no turn (`attention`, direct submits). To open the transcript at it, call
`GET /sessions/{id}/conversation/turns/{turn_id}`, which returns `{turn, index, total_turns,
projection_revision, requested_turn_id}` in the same absolute index space as the windowed conversation read,
then load the window with `after=index-1` (or `before`/`limit`). A 404 means the turn is not
in the current projection; open the session without an anchor and explain that the exact
location is unavailable. Observation-order display fragments retain `source_turn_id`
and `source_turn_terminal` in `metadata.conversation_timeline`. The resolver accepts
an exact row ID first, or the unique terminal fragment of that durable source ID.
Clients anchor on the returned `turn.id`, requiring `requested_turn_id` to match the
request when the IDs differ. Never guess by text, timestamp or raw log sequence.

| Method and path | Purpose |
|---|---|
| `GET /notifications` | Feed for the caller (owner-scoped; admins see all). See the query parameters below. |
| `GET /sessions/{id}/notifications?after=&limit=` | One session's notifications, ascending. Uses the session access check. |
| `POST /sessions/{id}/notifications` | Direct submit (operator or external agents). Body: `NotificationDraft` + `idempotency_key` (required). Returns the notification (201, or 200 when deduped). Feed-only: `session_seq` is null. |
| `GET /notifications/read-state` | `{read_through_seq, revision, unread_count, head_seq}` |
| `PUT /notifications/read-state` | `{read_through_seq, expected_revision}`. The watermark only moves forward; 409 on a revision conflict. |
| `PUT /notifications/{id}/read` | No body; acknowledge one visible notification for the caller, idempotently. Returns `{id, read: true, read_state: {read_through_seq, revision, unread_count, head_seq}}`. Missing/invisible IDs return404. |
| `GET /notifications/rules`, `POST /notifications/rules`, `PUT /notifications/rules/{id}`, `DELETE /notifications/rules/{id}` | Owner-scoped rule CRUD. |
| `GET /notifications/{id}/deliveries` | Delivery status rows for one notification. |
| `GET /notifications/sinks` | Available sink names for the rule UI: `[{name, label, requires_integration}]`. |
| `GET /notifications/{id}/image[?variant=thumb]` | The stored image bytes (§11), with the same read access as the notification. 404 when there is no stored image. |

`GET /notifications` query parameters:
- Paging: `limit` (default 50, max 200), `before=<seq>` (newest first), or
  `after=<seq>` (ascending, for gap-fill).
- Filters: `kind` (CSV), `min_severity`, `source` (CSV), `session_id`, `project_id`.
- `unread=true|false`.
- Response: `{items, next_before, head_seq, read_through_seq, unread_count, revision}`.
- Individual acknowledgements increment the same reader revision only on first insert;
  retries do not increment it. Mark-all uses the existing watermark CAS, so a concurrent
  item acknowledgement can require the usual read-and-retry on409. Both unread filters
  and counts exclude individually acknowledged items.

Rule JSON:
```json
{"id":"uuid","name":"…","enabled":true,
 "match":{"kinds":[],"min_severity":"info","sources":[],"project_ids":[],"session_ids":[]},
 "sink":"telegram","integration_connection_id":"…|null","config":{},
 "quiet_hours":{"start":"22:00","end":"07:00","timezone":"Europe/London","allow_min_severity":"critical"}|null}
```
An empty list in `match` means "any".

## 5. Live events (shared: core, web)

- Event: `EventType.SESSION_NOTIFICATION = "session_notification"`, on the
  existing `/api/v1/forge/sessions/stream`. `data` is the `NotificationResponse`
  without `read`.
- Only the owner (or an admin) receives it. Filter it in the SSE handler before
  sending; other event types are unchanged.
- The Guild facade forwards it unchanged, adding `instance_id` as it already does
  (and routing the image URLs, §6).
- A notification with an image is broadcast once, when its image copy settles, so
  the event carries the same `image` object as the feed. Its event may therefore
  arrive after a later notification's; `seq` order in the feed is unchanged.
- Clients recover gaps with `GET /notifications?after=<last seen seq per instance>`.
- Sleipnir: `volundr.session.notification` is registered and mirrored from the
  broadcaster, like needs_input.

## 6. Guild facade on niuu, in `rest_volundr.py` (core)

- Proxy every route in §4.
- `GET /notifications?all_instances=true` fans out to the visible instances and
  merges newest first by `(created_at, instance_id, seq)`. The web always sends
  `all_instances=true`, as it does for `/sessions/stream`. Without it, the request
  goes to the local instance, or to the one named by `instance_id`.
  - The cursor is opaque: base64url JSON `{instance_id: seq}` for `before`, and
    the same for `after`.
  - It reports `X-Forge-Unavailable-Instances`.
- Read state: `GET` aggregates `unread_count` and returns a per-instance map.
  `PUT` accepts a per-instance map. Per-host feed summaries also carry optional `revision`
  (absent on old hosts).
- `PUT /notifications/{id}/read?instance_id=<owning-host>` goes only to that host,
  never fans out; the receipt adds `instance_id`. An old host returns404/405/501: clients
  must report the missing API, not substitute a watermark write.
- Session-scoped routes go to the owning instance (`_find_session_owner`).
- Rules and sinks go to the selected instance, local by default.
- Push devices (`POST /devices`, `GET /devices`, `DELETE /devices/{token}`) fan out
  to every visible instance, because each node pushes to the devices registered
  with it. They succeed only when every instance agrees, and never report a
  partial result:
  - `POST` answers 201 with one instance's record when all accepted. A node's 4xx
    refusal propagates as that status; an unreachable node or 5xx is 502. The
    detail names each failing instance. Registration is idempotent per node on
    (owner, token), so the client retries.
  - `DELETE` answers 204 when all instances removed it or no longer know it (404);
    otherwise the same error shape.
  - `GET` returns the union de-duplicated by token (first instance wins), and fails
    naming an unreachable instance instead of setting
    `X-Forge-Unavailable-Instances`, since a partial list reads as "not registered".
- Images: every notification the facade returns (feed pages, session lists, submits,
  SSE events) has its `image.url` / `image.thumbnail_url` rewritten to the same path
  plus `instance_id=<owning host>`. `GET /notifications/{id}/image` goes to the host
  named by `instance_id` (the default host otherwise), like `PUT …/read`; the host
  applies the notification's read access. A single Forge node returns the plain URL.

## 7. Delivery (delivery workstream)

- `src/niuu/ports/notifications.py`: `NotificationSink` (`name`,
  `async send(message: OutboundNotification) -> DeliveryResult`). It raises
  `NotificationDeliveryError` (retryable or permanent), never swallows errors.
  `OutboundNotification` is the rendered, sink-neutral message: title, body, deep
  link, severity, kind, session label.
- Adapters move to `src/niuu/adapters/notifications/{telegram,webhook}.py`, with
  re-exports kept at the old Ting class paths.
- A push sink wraps Volundr's push channels.
- Volundr `NotificationDispatcher`: a background loop that claims due deliveries
  (`FOR UPDATE SKIP LOCKED`, lease), resolves the sink and settles each one.
  - Sink resolution: an `integration_connection_id` goes through the owner's
    MESSAGING integration connection (the dynamic class path plus credential,
    Ting's resolver pattern moved to niuu). Otherwise it uses the named sink from
    `notifications.sinks`, configured with the dynamic `adapter:` + kwargs rule.
  - Retries back off exponentially up to `max_attempts`, after which the row is `dead`.
  - Every interval, lease, backoff and batch size comes from `NotificationsConfig`.
- Quiet hours and the rate limit are evaluated at claim time; a held-back message
  becomes `suppressed`.

## 8. Forge MCP (skuld workstream)

Broker loopback routes, guarded by `Authorization: Bearer <launch secret>`:

| Route | Contract |
|---|---|
| `GET /api/forge-mcp/tools` | MCP tool list: name, description, inputSchema. |
| `POST /api/forge-mcp/tools/{name}` | Body: tool arguments. Returns `{content: [{type:"text",text}], structuredContent?, isError}`. |

- The launch secret is random, written 0600 to `<runtime dir>/forge-mcp.token`,
  and regenerated per broker start.
- The stdio server `python -m skuld.forge_mcp --broker-url http://127.0.0.1:<port>
  --token-file <path>` implements MCP (`initialize`, `tools/list`, `tools/call`,
  `ping`) over stdio and forwards to those routes. It holds no Forge credential.
- It is injected by Skuld as the built-in MCP server `forge` for every engine
  that supports MCP. Opt out with `SKULD__FORGE_MCP__ENABLED=false`.

| Tool | v1 access | Broker behaviour |
|---|---|---|
| `environment` | default | Session id and name, node, workspace, engine, model, project, Forge URL, runtime version. No secrets. |
| `notify` | default | Validates a `NotificationDraft` (agent kinds only), appends the turn, flushes the log, returns `{notification_id, turn_id, session_seq, state}`. `state` is `committed` once Forge acked the flush, else `pending`. |
| `list_notifications` | default | `GET /notifications`, bounded. |
| `list_sessions`, `get_session` | default (read) | Forge REST. Qualify each session with its instance id. |
| `session_transcript` | default (read) | The tail of a session's conversation (bounded turns and characters). |
| `send_message`, `message_status` | grant `message` | `POST /sessions/{id}/messages` with a stable `request_id`, and the delivery status. |
| `create_session`, `start_session`, `stop_session` | grant `lifecycle` | Existing lifecycle routes. No delete. |

Grants come from the scoped session token (§9). Without a grant the tool returns
`isError` with an explanation and is still listed, so the model learns why.

## 9. Scoped session credential (auth workstream)

- Add scopes to `KNOWN_WORKLOAD_SCOPES`: `forge:notify`, `forge:session:read`,
  `forge:session:message` and `forge:session:lifecycle`.
- At launch, Volundr mints a session-bound workload token (`token_use` =
  `forge_session`, `session_id`, owner, scopes). The defaults are `forge:notify`
  and `forge:session:read`, plus whatever the launch-spec or session-create
  `forge_mcp.grants` add.
- Skuld receives it as `SKULD__FORGE_MCP__TOKEN`. It is used only by the MCP
  proxy client, never by the existing broker→Forge calls, and never copied into
  the model's environment.
- Volundr enforces the scopes with `require_scope` on the notification, session
  read, message and lifecycle routes whenever the principal carries a scoped
  `forge_session` token. A token bound to one session cannot notify as another
  session.
- The facade forwards the token and enforces the same scopes.
- A Forge-hosted `POST /mcp/forge` (Streamable HTTP, JSON response mode) serves
  the same tools for external agents. It uses the caller's own auth and the
  shared tool definitions from `src/niuu/forge_mcp/`.

As built (auth workstream). The operator guide is
[`docs/operator/forge-mcp.md`](../operator/forge-mcp.md).

- **Claims.** The token carries `token_use=forge_session`, `sub` (the owner),
  `tenant_id` and `scopes`. The bound session is in `workload_session_id`, the same
  claim OpenShell session tokens use, and the launch is in `workload_launch_id`.
- **Lifetime.** It is tied to the launch. Every start re-mints the token and records
  the new launch on `sessions.workload_config.forge_mcp`, which revokes the previous
  one. Stopped, archived or deleted sessions revoke it too. `exp` is a configurable
  backstop (30 days); there is no refresh route.
- **Grants** persist in `sessions.workload_config.forge_mcp.grants`, so no migration
  was needed. The session-create field is `forge_mcp: {grants: [...]}`.
- **Enforcement.** Forge verifies the token in every identity mode, and admits it
  only on an allow-list of routes (`niuu.domain.services.forge_session_policy`);
  everything else is 403.
- **Facade.** The facade applies the same allow-list, but never forwards the token
  to a remote node. Peer supervision with a session token is limited to its own
  node (403).
- **Endpoint path.** The HTTP endpoint is `POST /api/v1/forge/mcp`, so the Guild
  host's Forge route domain dispatches it. `notify` there is a feed submit and takes
  a required `idempotency_key`.

## 11. Notification images (shared)

**Input.** `NotificationDraft.image` is an optional `NotificationImageRef`:
`{"file_id": "pf_<32 hex>"}` (the id `present-file` returned) **or**
`{"url": "https://…"}` — exactly one — plus optional `alt` (at most
`MAX_IMAGE_ALT_CHARS` = 300 characters). Strict: extra keys, non-https URLs and URLs
with credentials are refused. The MCP `notify` tool (transcript and feed modes) and
`POST /sessions/{id}/notifications` accept it.

**Copy.** Forge records the notification and a `pending` row in
`forge_notification_images` (migration `000090`) in one transaction, then copies the
bytes once in the background: `file_id` through the session's broker
(`GET {broker}/api/files/presented/{file_id}`, resolved like the presented-file proxy),
`url` by HTTPS GET (each redirect hop must be https and, unless
`notifications.images.allow_private_networks`, resolve only to public addresses). The
response must declare and decode as `image/png|jpeg|gif|webp`, within
`MAX_IMAGE_BYTES` (10 MiB) and `MAX_IMAGE_PIXELS` (40 MP). Forge stores the original
bytes and a thumbnail (long side `notifications.images.thumbnail_max_side`, 320 by
default; PNG when transparent, JPEG otherwise).

**State.** `image_state` is `pending` until the copy settles, then `ready` (with
`image`) or `failed` (with `image_error`). The notification is never withheld or
rolled back for its image, and a failed copy is final: Forge neither retries it nor substitutes anything.
Replays never copy twice (the image row is keyed by the deterministic notification id).

**Route.** `GET /api/v1/forge/notifications/{id}/image` serves the original, and
`?variant=thumb` the thumbnail, with the stored content type,
`Cache-Control: private, max-age=<notifications.images.cache_max_age_seconds>, immutable`
and `X-Content-Type-Options: nosniff`. It requires exactly what reading the item
requires (`forge:session:read` for scoped tokens, then owner or tenant admin); 404
otherwise and whenever no image is stored.

## 12. Questions, asks and runtime requests (shared)

Two kinds of "needs you" items share the feed. They stay distinct because they are
answered differently.

**Notice questions (agent `notify`, direct submit, resident notify).** `question: true`
declares a question the user must answer; a notice that sets `question` (true or false)
is never inferred to be one. Its reference is `question:<host>:<notification_id>`.
Later notices refer to it with `about_question: {id, action}`, `action` one of
`remind|replace|relay|resolved|withdrawn` (only the asking session may do anything but
`relay`; the control plane enforces that). `ask: {items: [...]}` (only with
`question: true`) structures it:

| Item field | Rule |
|---|---|
| `id` | 1–64 chars, `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, unique in the ask |
| `kind` | `question` or `action` (an action asks the user to report done/not done; it never executes anything) |
| `text` | 1–2000 chars, nonblank |
| `header` | optional, 1–80 chars |
| `options` | optional, 1–8 `{label, description?, recommended?}`; labels 1–120 chars, unique per item; descriptions ≤ 500; `recommended: true` on at most one option per item (a label ending in `(Recommended)` counts as one, so older producers keep working) |
| `multi_select` | optional boolean; omitted means false |
| `allow_text` | optional boolean; omitted means true; a question with `false` must offer options |
| `default` | optional `{option, after}`: what happens if the user does not answer. `option` is one of the item's option labels or `none`; `after` is an ISO-8601 timestamp with a timezone, or an ISO-8601 duration counted from the notification (`PT4H`, `P1D`). Forge records it and acts on nothing; the asking session carries it out (LEX-1671) |
| `deadline` | optional ISO-8601 timestamp with a timezone: when the answer is needed |

At most 8 items and 32768 UTF-8 bytes of compact ask JSON; optional fields are omitted,
never null; NUL is refused. The fields live in the notification's `metadata` and are
served on the read wire and the live event exactly as sent. The answer is an ordinary
message to the asking session: `POST /sessions/{id}/messages` with a stable
`request_id` (through the Guild facade, `?scope=local` pins the session's node): 200
delivered, 202 pending, the same id with different content 409 (`request_id_conflict`;
409 also when the pod is unreachable). Delivery is not resolution: the asking session confirms it later with
`about_question` (`resolved`).

**The question standard (LEX-1597, LEX-1671).** An agent's `decision` (the user must
choose) or `attention` (the user must act or unblock) is a question: `question: true`,
an `ask` with 2–4 options, one `recommended`, and a `default`. The text is
`niuu.question_standard.QUESTION_STANDARD`; the `notify` tool, the Forge MCP server
instructions and the session prompt all carry it. The `notify` tool lints before it
records:

- a `decision`/`attention` with no `ask`, no `?` in its title and no options listed in
  its body (two or more lines starting `-`, `*`, `•`, `1.`, `a)`…) is recorded as
  `info`. The tool result adds `kind: "info"`, `requested_kind` and a `warnings` entry
  quoting the standard;
- one with an `ask` whose choice has no recommended option, or whose items have no
  `default`, is recorded as sent, with a `warnings` entry.

Direct REST submits (`POST /sessions/{id}/notifications`) are not linted; they validate
the fields above.

**Runtime requests (Forge's system `attention` item).** When a session (or resident)
blocks on AskUserQuestion, a confirmation or a permission, Forge records an
`attention`/`system` item. `input_request: {kind: question|confirmation|permission,
request_id}` names the pending request (`request_id` null when the runtime reported
none). It is answered where the transcript's card answers it, on the session socket
(`ask_user_answer` with that `request_id`, or the permission response), never through
the notification; the item is marked read when the session stops waiting. Such an item
carries no `question`/`ask`.

**Review gates (Forge's system `attention` item).** A workflow gate that waits for a
person raises the same `attention`/`system` item, projected from its `workflow_gate`
log frame with dedupe key `workflow-gate:{session}:{gate_id}`. Its `input_request` is
`{kind: workflow_gate, request_id: <gate id>}`. It is answered on
`POST /sessions/{session_id}/workflow/gates/{request_id}/resolve` (header
`x-niuu-workflow-gate-intent: resolve`), not on the session socket, so a client must
route on `kind`. The gate's decided frame marks the item read and resolves it, wherever
the decision was made; a session leaving `awaiting_input` does not touch it.

**`notify` schema.** The advertised input schema's root stays a plain object (no
`allOf`/`if`): Claude Code drops a tool whose root schema has a conditional from its
catalog while the server stays connected. `ask` → `question: true` is enforced by
`NotificationDraft` before anything is written.

## 13. Speak intent (shared)

A notification may ask to be spoken aloud to its owner (LEX-1536). Forge carries the
intent and nothing more: it does not deliver, schedule or speak it. A reader (the
Lexi agent service) decides whether and when the phone speaks it.

**Input.** `NotificationDraft.speak` is an optional `NotificationSpeak`:
`{"text": "…", "priority": "now" | "next_window"}`. Strict: extra keys are refused.

| Field | Rule |
|---|---|
| `text` | trimmed, then 1–`MAX_SPEAK_TEXT_CHARS` (600) characters; no NUL |
| `priority` | `now` (default) or `next_window` (the next good moment) |

Only agent kinds (`milestone`, `decision`, `attention`, `error`, `info`) may carry
it; a draft of kind `reply_ready` with `speak` is refused. The MCP `notify` tool
(transcript and feed modes) and `POST /sessions/{id}/notifications` accept it; an
invalid one is an MCP tool error or HTTP 422 and records nothing.

**Storage.** Migration `000097_forge_notification_speak` adds `speak_text` and
`speak_priority` to `forge_notifications`, set together or both null, with a check
that repeats the rules above.

**Read.** `speak` is on every `NotificationResponse` (§4): `GET /notifications`,
`GET /sessions/{id}/notifications`, the submit response, and the
`session_notification` live event (§5); `null` when the notification has none. The
MCP `list_notifications` summary includes it when set.
